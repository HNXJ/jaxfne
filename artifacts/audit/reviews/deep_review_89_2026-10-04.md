# 5. Biggest software weakness: complexity concentration

This is where I would now focus engineering effort.

Some modules are very large:

```text
emitters.py            5077 LOC
tfne.py                3534
tutorial_utils.py       2159
optim/core.py           2001
_config.py              1830
_model_simulate.py      1720
fields/proxy.py         1625
_signals.py            1599
neuronal_tensor.py     1502
_construct_core.py     1434
validation.py          1386
_model_tune.py         1374
```

Large files are not intrinsically bad. But here they indicate **semantic density is becoming concentrated in implementation hubs**.

`emitters.py` at ~5k LOC is the clearest case.

The risk is:

\[
P(\text{regression}\mid\Delta)
\uparrow
\quad\text{as unrelated semantics share a module}.
\]

The tests currently compensate very well. But tests should not become the only thing keeping increasingly monolithic implementation surfaces safe.

### Recommendation

Do **not** perform a broad aesthetic refactor.

Instead split only when there is an actual semantic boundary:

```text
emitters/
    base.py
    izhikevich.py
    receptors.py
    recurrent.py
    multicompartment.py
    registry.py
```

while keeping the existing import surface unchanged.

Same principle for `tfne.py`: parser/normalization/realization/indexing could eventually become internal modules behind one public compiler surface.

This would move maintainability from **84 → ~90** without changing scientific behavior.

# 10. Analysis migration exposes an important remaining defect class

The current todo identifies three old metric semantics:

- population-summed Fano factor;
- `burst_index` ignoring `bin_ms`;
- unbinned pairwise spike correlation.

The code now explicitly deprecates the misnamed Fano metric rather than silently changing its output.

That is good compatibility engineering.

But it reveals a larger lesson:

> **analysis functions require the same semantic rigor as simulation kernels.**

A scientifically wrong metric can invalidate conclusions even when the simulator is perfect.

Moving canonical analysis toward jnwb is therefore a good direction, provided JaxFNE keeps the bridge thin and does not create a hard architectural dependency between simulation and analysis.

# My strongest criticism

JaxFNE's largest risk has changed.

Earlier the likely failure was:

> **semantic inconsistency / implementation bugs.**

The test/harness architecture has substantially controlled that.

The current danger is:

\[
\boxed{\text{framework sophistication} > \text{scientific evidence density}}
\]

There are many abstractions—TFNE, JDNA, H, HDP, source/field/probe, optimization, Atlas, bridges—and the abstractions are increasingly good.

But every additional abstraction now creates scientific debt unless an experiment establishes:

\[
\text{what observable requires it?}
\]

So I would impose a strong post-0.5.5 rule:

\[
\boxed{
\text{new mechanism}
\Rightarrow
\text{reference model + discriminator + reduction test}
}
\]

rather than merely unit tests.

That is already philosophically present in the research firewall: literature → equations/units → isolated reproduction → sensitivity → generic test → implementation decision. 05_RESEARCH_EVIDENCE_REFERENCES…

Make that the dominant development mode.
